# 海康相机目标识别接入方案

## 1. 目标与边界

在保持海康 MVS 取流稳定性的前提下，将
`D:/study/LicheeRV/resouce/dataset_raw/gc4653_20261027_session_3201/model/best.onnx`
接入当前取流程序，完成目标检测、传统视觉复筛、卡尔曼跟踪、未来位置预测和可选串口输出。

第一阶段只做 PC 端检测叠框和性能验证，不直接控制发射机构。相机始终使用海康 MVS SDK，不改为 V4L2 或 OpenCV 摄像头接口。

## 2. 后端选择

当前电脑运行 ONNX 时默认是 **CPU 推理**，不会自动使用 NPU。后续设备可以替换推理后端：

| 设备 | 推理方式 |
|---|---|
| 当前 x86 电脑 | ONNX Runtime CPUExecutionProvider |
| NVIDIA GPU 电脑 | ONNX Runtime CUDA/TensorRT Execution Provider |
| LicheeRV Nano | `.cvimodel` + CVI NPU Runtime |
| 其他设备 | 新增对应 `InferenceBackend`，不修改相机和跟踪代码 |

当前 `best.onnx` 是 YOLO26n 端到端输出，项目记录为 `1x300x6`，包含 `TopK/GatherElements`。PC 端先用 ONNX Runtime 验证；LicheeRV 端应从 `best.pt` 重新导出 raw detection head 后再转换为 `.cvimodel`，不要直接假定当前 ONNX 可以被 NPU 编译。

## 3. 最小改动原则

不重构现有目录，不修改 MVS 相机启动方式，不覆盖原始模型，不引入与任务无关的依赖。

建议只新增以下模块：

```text
Vision/
  DetectionTypes.hpp       # 帧、检测框、跟踪结果结构
  InferenceBackend.hpp     # 推理后端统一接口
  OnnxRuntimeBackend.*     # 当前电脑 CPU 推理
  VisionPipeline.*         # 推理、复筛、跟踪总流程
  TargetTracker.*         # 卡尔曼跟踪和未来位置预测
```

当前 `CameraSetting` 只增加一个视觉管线成员和一次提交调用；不把模型代码直接写进 MVS 采集循环。

## 4. 推荐数据流

```text
海康 MVS 采集线程
  -> 有界帧池（3~4 帧，满时丢旧帧）
  -> VisionPipeline 推理线程（只处理最新帧）
  -> YOLO 后处理
  -> ROI 传统视觉复筛
  -> 卡尔曼跟踪
  -> 8 秒后目标位置预测
  -> 最新状态输出/显示/录像/串口
```

第一版采用单进程多线程，避免进程间拷贝和 IPC 延迟。采集、推理、输出相互隔离；只有在后续需要故障隔离或独立网页服务时，才考虑共享内存多进程。

## 5. 线程职责

### 5.1 采集线程

- 独占 MVS 相机句柄；
- 调用 `MV_CC_GetImageBuffer`；
- 完成 Bayer 转换或缩放；
- 将帧写入预分配帧池；
- 尽快调用 `MV_CC_FreeImageBuffer`；
- 不等待推理、录像、窗口和串口。

禁止让推理线程长期持有 MVS SDK 的原始 buffer。禁止无限制地对完整 1440x1080 图像进行多次 `clone()`。

### 5.2 推理线程

- 取最新帧；
- 执行 letterbox 和模型输入转换；
- 调用统一推理后端；
- 解码模型输出；
- 输出检测框和推理耗时。

推理队列最多保存 1~2 帧。新帧到达时覆盖旧待处理帧，避免延迟不断增长。

### 5.3 复筛与跟踪

第一版与推理线程放在同一条工作线程中，减少线程切换：

```text
模型框 -> ROI 裁剪 -> 颜色/亮度/轮廓/面积筛选 -> 几何约束 -> 卡尔曼更新
```

只有复筛耗时经过实测明显影响推理，才拆成独立线程。

### 5.4 输出线程

显示、录像、RTSP 和串口均只消费“最新结果”，不阻塞采集线程和推理线程。串口按固定周期发送最新目标状态，不为每个检测结果排队发送。

## 6. 推理接口

相机和跟踪代码不得依赖 ONNX Runtime 或 CVI Runtime 的具体 API：

```cpp
class IInferenceBackend {
public:
    virtual ~IInferenceBackend() = default;
    virtual bool load(const std::string& modelPath) = 0;
    virtual bool infer(const cv::Mat& input,
                       std::vector<float>& output) = 0;
    virtual std::string name() const = 0;
};
```

实现顺序：

```text
OnnxRuntimeBackend（CPU）
CudaOnnxBackend 或 TensorRtBackend（GPU，可选）
CviNpuBackend（LicheeRV，可选）
```

## 7. 卡尔曼跟踪与未来位置预测

### 7.1 重要区分

卡尔曼滤波器负责估计当前目标状态；“预测 8 秒后的位置”是基于当前状态向前外推，不能把 8 秒后的预测位置当成当前观测再次更新滤波器。

### 7.2 配置项

预测时间必须可配置，不写死 8 秒：

```yaml
vision:
  tracker:
    enabled: 1
    prediction_horizon_seconds: 8.0
    max_prediction_seconds: 10.0
    lost_timeout_ms: 250
    min_confirm_frames: 3
```

后续改成 10 秒时只修改 `prediction_horizon_seconds`，不修改算法代码。

### 7.3 状态模型

第一版使用可读性较高的二维匀速模型：

```text
state = [x, y, vx, vy]
```

检测有效时更新 `x/y`；检测丢失时只进行短时间预测；对外输出时使用：

```text
future_x = x + vx * prediction_horizon_seconds
future_y = y + vy * prediction_horizon_seconds
```

如果后续目标运动明显加速度，再升级为 `[x, y, vx, vy, ax, ay]`，不要一开始引入复杂模型。

### 7.4 可靠性限制

8 秒外推对匀速模型要求很高，必须同时输出预测质量：

```text
tracking_state
prediction_horizon_seconds
future_x/future_y
prediction_valid
uncertainty
```

当协方差、速度突变或连续丢失超过阈值时，`prediction_valid=false`，不能继续输出看似精确的未来位置。8 秒和 10 秒都应通过实测验证，不能仅凭 FPS 判断可用性。

在现有 YAML 中增加视觉配置，不改变原有 camera 配置：

## 9. 实施步骤

1. 只读检查当前工程、OpenCV、编译方式和 MVS 依赖。
2. 用离线图片加载 `best.onnx`，确认输入尺寸、输出形状、坐标格式、置信度和类别编号。
3. 新增检测结构和 `IInferenceBackend`。
4. 实现 PC CPU ONNX Runtime 后端，完成单图推理测试。
5. 接入海康实时帧，只做最新帧推理和叠框显示。
6. 增加采集、推理、显示、端到端 FPS 和 p50/p95 延迟统计。
7. 增加 ROI 传统视觉复筛。
8. 增加卡尔曼当前状态和可配置未来位置预测。
9. 增加串口线程，但默认关闭串口。
10. 进行至少 30 分钟稳定性测试，再考虑 GPU/NPU 后端。

## 10. 验收标准

- MVS 相机可以正常打开、停止和释放；
- 模型加载失败时明确报错并安全退出；
- 检测框坐标与原图位置一致；
- 推理变慢时采集延迟不会无限增长；
- 队列深度有上限，旧帧会被丢弃；
- 8 秒预测值随配置修改生效；
- 改为 10 秒不需要重新编译；
- 丢失目标时不会继续输出无效预测；
- 录像、显示和串口异常不会拖死采集线程；
- `vision.enabled: 0` 时原有纯取流功能不变；
- 记录 Capture FPS、Inference FPS、End-to-End Latency、Dropped Frames、Tracking Lost Count。

## 11. 当前代码需要优先修正的问题

1. 当前录像和 `imshow` 共用 `OutputWorker`，需要与推理路径解耦。
2. 当前每帧复制成本较高，应改为有限帧池。
3. `OutputWorker::loop()` 中存在 `captureMs = captureMs` 变量遮蔽错误，导致显示采集耗时不可信。
4. 录像写盘不能阻塞采集和推理。
5. FPS 必须分为采集、推理、显示和端到端四类。

## 13. 给执行代理的要求
