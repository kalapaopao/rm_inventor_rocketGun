# 串口链路测试

两个入口，职责不同，别混用：

| 入口 | 测的是什么 | 何时用 |
|---|---|---|
| **`show --serial-test`**（正式） | **项目正式发送模块** `vision::SerialOutput` 能不能正常往电控发帧 | 日常验收、换转接板后确认、比赛前检查 |
| `tools/serial_link_test.c`（应急诊断） | 仅硬件链路：用 libusb 用户态直驱 CH341，绕过缺失的内核驱动 | 手上只有 CH341、没有 `/dev/ttyUSB*` 时定位"到底是芯片/接线的问题还是驱动的问题" |

> **判定原则**：`--serial-test` 通过 = 项目能正常发数据给电控。
> 应急诊断工具通过 ≠ 项目能发，因为它走的不是项目的发送路径。

---

## 一、`show --serial-test`（正式）

### 它做什么

不打开相机、不启动视觉管线，直接实例化**正式发送模块** `vision::SerialOutput`，
只把"目标来源"换成恒为"无新鲜结果"，于是每个周期发出协议 v1 的无目标帧：

```text
A5 00 00 00 22 E8      TARGET=0，YAW=0，CRC16-Modbus
```

这与正式运行中"链路活着但视野内没目标"走的是**同一条代码路径**：同一个 `SerialOutput::loop`、
同一个 `writePacket`、同一套半帧保护。所以它通了，就说明正式发送链路是通的。

参数全部取自 `Camera/camera_config.yaml`：

```yaml
vision:
  serial_port: "/dev/ttyUSB0"
  serial_baud: 115200
  serial_period_ms: 50
```

### 用法

```bash
cd /rm_inventor_fly

# 先停掉自启动服务，避免两个进程抢串口
sudo systemctl stop dart-vision.service

# 跑测试（Ctrl+C 结束并打印汇总）
sudo ./build/Camera/show --serial-test

# 或经启动器（自动带 --config）
bash tools/run_rk3576.sh --serial-test
```

每秒输出一行，**同时打印实际发送的字节**，既能看到发什么、也能看到帧数在涨（证明真的在跑）：

```text
[link] 串口自检 /dev/ttyUSB0 @115200 8N1 / 50ms
[link] 发送帧 A5 00 00 00 22 E8  (SOF=A5 TARGET=0 YAW=0 CRC16)
[SerialOutput] started on /dev/ttyUSB0 @115200, period 50 ms
[link] 1s 帧=20 错误=0 20.0Hz  发=A5 00 00 00 22 E8
[link] 2s 帧=40 错误=0 20.0Hz  发=A5 00 00 00 22 E8
...
[link] 76 帧 / 456 B / 0 错误 / 3.8 s / 20.0 Hz
[link] PASS：正式发送模块正常，项目可发帧给电控
```

`[SerialOutput] started on ...` 这行来自正式模块本身，是"真的开起来了"的第一道证据；
之后每秒的 `帧=` 递增就是持续发送的证据。

### 判据

| 输出 | 含义 |
|---|---|
| `PASS` | 正式发送模块正常，项目能发数据给电控 |
| `FAIL：正式发送模块无法在 /dev/ttyUSB0 上启动` | 设备节点不存在或打不开——**正式程序同样会失败**，先解决硬件/驱动 |
| `FAIL：发送线程中途停止` | 写错误触发半帧保护，正式运行也会停发 |
| `FAIL：一帧都未发出` / `出现 N 次写错误` | 端口异常 |

> Ctrl+C 与写操作竞争时，发送线程可能在退出瞬间停掉并留下一次写错误。
> 这是退出时序，不是链路故障：只要是你主动结束（`g_stop` 已置位），工具会打印
> `注：退出瞬间发送线程停止（Ctrl+C 与写操作竞争），非链路故障` 并仍判 PASS。

### 已验证（2026-11-18，虚拟串口 PTY）

用 PTY 模拟一个可用的串口，验证 PASS 路径与退出行为：

```text
[link] 1s 帧=20 错误=0 20.0Hz  发=A5 00 00 00 22 E8
[link] 3s 帧=60 错误=0 20.0Hz  发=A5 00 00 00 22 E8
[link] 76 帧 / 456 B / 0 错误 / 3.8 s / 20.0 Hz
[link] PASS：正式发送模块正常，项目可发帧给电控
```

- 对端收到的帧**全部 CRC16 正确、0 次重同步**，帧内容 `A5 00 00 00 22 E8`；
- `Ctrl+C` / `timeout -s INT` 均能干净退出，不误报故障；
- 真实 CH341 转接板（无 `/dev/ttyUSB0`）→ 如实 FAIL，与正式程序表现一致。

### 当前板端的已知结论

板端内核 `6.1.115-rt16-g469da534041d` 配置为 `# CONFIG_USB_SERIAL_CH341 is not set`，
且驱动全部编入内核镜像（无 `/lib/modules`）。因此：

- **CH340/CH341 转接板**：`lsusb` 可见 `1a86:5523`，但**永远没有 `/dev/ttyUSB0`**，
  `--serial-test` 必然 FAIL——这不是测试工具的问题，是正式程序也发不出去。
- **CP2102 / FT232**：内核已内建驱动（`=y`），插上即出 `/dev/ttyUSB0`，`--serial-test` 应当 PASS。

> 结论：**转接板必须换 CP2102 或 FT232**。换完 `sudo systemctl restart dart-vision.service` 即可正式发数据。

## 二、`tools/serial_link_test.c`（应急诊断，仅 CH341）

仅当"手上只有 CH341、内核没驱动"时使用：用 libusb 在用户态直接驱动 CH341/CH340，
寄存器序列照抄 Linux v6.1 `drivers/usb/serial/ch341.c`，不依赖内核模块。

```bash
cd /rm_inventor_fly
sudo apt-get install -y libusb-1.0-0-dev     # 只需一次
bash tools/build_serial_link_test.sh          # 产物 build/serial_link_test

sudo ./build/serial_link_test probe           # 认芯片 + 配 115200 8N1
sudo ./build/serial_link_test tx 30           # 20Hz 发 30s 无目标帧
sudo ./build/serial_link_test loop 50         # 自回环（先短接 TX-RX）
sudo ./build/serial_link_test rx 10           # 只收并解码
```

它只证明"芯片 + USB + 引脚能发字节"，**不证明项目的发送模块可用**。

### 2026-11-18 实测记录（CH341）

| 轮次 | 接法 | 结果 |
|---|---|---|
| tx 10 | 拓展坞 | 199 帧 / 1194 B / 0 错误 |
| tx 300 | 直插板子 | 760 帧后芯片掉线（`LIBUSB_ERROR_NO_DEVICE`，38s 处） |
| tx 120 | 拓展坞 | 2389 帧 / 14334 B / 0 错误 / 19.9 Hz，全程稳定 |

- 发送链路功能正常，累计 3300+ 帧零错误，**电控端确认收到**。
- 掉线是**间歇性**的，与拓展坞无关；怀疑转接板接触/供电或 TTL 侧电气冲击。

## 三、接线检查清单

| 项 | 要求 |
|---|---|
| TX/RX | 板 TX → 电控 RX，板 RX → 电控 TX（**交叉**） |
| GND | **必须共地**，否则收不到也容易把芯片拉挂 |
| 电平 | 转接板跳线 **3.3 V TTL**；禁止 5 V / 1.8 V 直连 |
| 串口参数 | 双方 115200、8N1、无流控 |
| 设备节点 | 换 CP2102/FT232 后 `ls /dev/ttyUSB*` 应立即出现 |
